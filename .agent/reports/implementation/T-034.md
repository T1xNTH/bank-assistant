## Scope

Issue #75: Error Trigger → PII-free operator email through Mailpit; connect intake
error workflow and document failure handling, setup and recovery. Implementation
uses merged T-033 source e951ce6; no API contract or runtime application changes.

## Changes Made

- Stable `bankErrorHandler` export, allowlisted metadata sanitizer and fixed SMTP
  recipient. Error handler does not save execution payloads or link to itself.
- Intake links the handler; existing fail-closed HTTP/job/poll branches retained.
  No automatic retries, duplicate job submissions or customer replies after error.
- Import handler before intake, both idempotently by ID.
- Document publishing both workflows, credential binding, API-off/429/503/failed
  verification, SMTP failure diagnosis and checking side effects before retries.
- Regression tests execute the real JS sanitizer with hostile free-text metadata,
  absent execution, malformed IDs, HTTP codes, job failure and trigger errors.

## Verification Evidence

- Real n8n 2.45.7 and Mailpit 1.33.0 with a controlled HTTP API fixture: eight
  automatic production-form scenarios passed. Job `failed`; 429 and 503 at
  Classify, Enqueue and Poll job; fixture API container stopped after job enqueue
  during Wait. Every execution failed at the expected node, emitted exactly one
  operator-only SMTP email and no approval/customer email. Messages excluded
  synthetic customer email, OTP/account markers, raw error body and service key.
  The HTTP fixture is not the application API or a model quality test.
- Fresh n8n volume: both CLI imports and re-imports passed with stable workflow
  IDs. Handler is published before intake for the actual automatic executions.
- `make check PY=python` in Linux QA container: Ruff passed; **1124 passed,
  2 skipped, 79 deselected** in 215.16 seconds; one upstream LangChain warning.
  Framework validation passed. Native framework validation and `git diff --check`
  also passed. Node.js was available, so sanitizer expression tests were executed.

## Findings

- n8n 2.45.7 refused to execute an unpublished error handler: `Workflow
  "bankErrorHandler" is not active and cannot be executed`. Current online docs
  say publishing is unnecessary. Live setup and runbook require publishing both
  on the pinned version; imported source remains safely inactive.
- Initial QA image lacked main's Langfuse dependency. Full checks install the
  repository-pinned `langfuse==4.18.0` in the ephemeral QA container.
- CLI task start rejected T-033's stale pending lifecycle despite approved/merged
  PR #98. ISSUE-030 records the discrepancy without changing dependency status.

## Limitations and Follow-up

- Operator email contains only allowlisted metadata; intake's failed executions
  still contain restricted data locally under existing 24-hour retention.
- SMTP failure cannot notify through the same SMTP transport. Runbook requires
  local execution/service inspection; no alternate transport is introduced.
- No actual long-duration 60-poll timeout or 24-hour approval test is claimed.
- Independent separate Claude review and counterpart PR approval remain pending.
  Draft report and administrative pending task are retained until dependency
  closure permits the normal CLI report/verify/review-request lifecycle.
